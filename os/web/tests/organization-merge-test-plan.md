## 1A. Что проверять у уже сделанных пунктов

Статус каждой проверки: NOT RUN, пока её не выполнил браузерный прогон.

1. Миграция `f2_res.ini`. В активном cfg после старта есть `system.f2_res_migrated=1`. При `ALTERNATE_AMMO_METRE=1` в cfg оказывается `ui.alternate_ammo_meter=1`, а не 0. `MAIN_MENU_SIZE` переносится в `ui.main_menu_scale_mode` (0–2). `DEATH_SCRN_SIZE` и `END_SLIDE_SIZE` больше 1 записываются уже ограниченными до 1. Ключи `screen.resolution_x/y`, `windowed`, `scale`, заданные оболочкой, не затираются значениями из `f2_res.ini`. Повторный старт с уже стоящим маркером не переписывает явно заданные UI-ключи.
2. Финализация сохранения. После обычного сохранения и после быстрого (F6 без окна) `slotdat.ini` с `CurrentSlot` есть в IndexedDB до сообщения об успехе. Перезагрузка страницы открывает тот же слот. Закрытие окна после этого сохранения не делает второй sync. Смена слота, загрузка и отмена публикуют новый слот одним sync. Ошибка записи слота не синхронизирует неполный сейв.
3. Ошибки IndexedDB. Подмена `IDBFS.syncfs` ошибкой: стартовая загрузка показывает текст в статусе и не запускает игру; `write_idbfs` не печатает `IDBFS saved` и отклоняет Promise. Отказ `navigator.storage.persist()` и отсутствие API не считаются ошибкой записи.
5. Хвост `SAVE.DAT`. Сейв, который upstream читает, несмотря на лишние байты, загружается. В логе есть предупреждение о несовпадении размера, игра не сбрасывается. При ошибке открытия, заголовка, обработчика или `sfallgv.sav` `_loadingMapId` возвращается в -1.

## 3. Изоляция и доказательства

- Использовать отдельный тестовый browser context/профиль с пустыми слотами. Не очищать и не перезаписывать личные сейвы пользователя. Не держать две одновременно работающие игры, записывающие одну IDBFS-базу.
- Тесты сайта выполняются на настоящем `https://fallout-nevada.ru/`, без подмены его движка, конфигов или игровой логики. Не использовать dev-флаги кандидата как доказательство работоспособности опубликованной версии.
- Для кандидата зафиксировать commit, upstream commit, все незакоммиченные изменения, SDK, параметры сборки, SHA-256 локальных JS/WASM, браузер, ОС, viewport, DPR, HiRes и состояние pointer lock. Одного commit недостаточно, если merge ещё не закоммичен.
- Для baseline зафиксировать время, URL, сведения о service worker/версии, config.mjs, filesVersion, SHA-256 распакованного индекса каждой игры и доступные ETag/Last-Modified движка. Если сайт или данные изменились посреди прогона, не смешивать результаты разных версий.
- Сохранять скриншоты ключевых экранов, логи, сведения о загрузке, архивы слотов и manifest. Например, вне git: `artifacts/merge-audit/<run>/<folder>/baseline/` и `candidate/`. Не коммитить игровые наборы, WASM, browser profile и временные логи вместе с планом.
- Каждый неизменяемый baseline-архив снабдить SHA-256, именем игры, folder, временем, слотом, описанием персонажа, карты/позиции, инвентаря и выполненных действий. Дополнительно сохранить перечень файлов, размеров и hash содержимого архива.
- PASS означает выполненную проверку с доказательствами. BLOCKED/NOT RUN не превращать в PASS. Ошибки скриптов сравнивать с baseline; не считать все INFO, попавшие в console.error, авариями.

## 4. Доступ к игровым данным: сначала прямой CORS

**Сначала проверить прямой доступ из браузера. Прокси больше не является обязательной частью установки.** Пользователь настроил Nginx; подтверждённые результаты приведены в конце документа. Доступность нужно повторять в новой среде: CORS зависит от Origin.

```bash
curl -I -H 'Origin: http://localhost:8766' 'https://fallout-nevada.ru/game/FalloutNevadaEng/index.txt.gz?v=1'
curl -I -H 'Origin: http://127.0.0.1:8766' 'https://fallout-nevada.ru/game/FalloutNevadaEng/ddraw.ini.gz?v=1'
curl -I -H 'Origin: https://example.com' 'https://fallout-nevada.ru/game/FalloutNevadaEng/index.txt.gz?v=1'
```

Для разрешённых Origin ожидать 200, точный `Access-Control-Allow-Origin` и `Vary: Origin`; для чужого Origin ACAO должен отсутствовать. Затем выполнить настоящий браузерный GET с localhost и 127.0.0.1: curl показывает заголовки, но сам политику CORS не применяет.

Пример проверки в `page.evaluate` на странице локального HTTP-сервера:

```js
async () => {
  const response = await fetch('https://fallout-nevada.ru/game/FalloutNevadaEng/ddraw.ini.gz?v=1');
  const bytes = new Uint8Array(await response.arrayBuffer());
  return { origin: location.origin, status: response.status, type: response.type,
    length: bytes.length, gzip: bytes[0] === 0x1f && bytes[1] === 0x8b };
}
```

- Проверить индексы и реальные файлы всех folder/версий. `index.txt.gz` — gzip, внутри windows-1251, строки `<size> <sha256> <path>`; штатный parseIndex это поддерживает. Сверять размер и SHA-256 РАСПАКОВАННЫХ файлов, как существующий fetcher.
- `useGzip=true`: ресурсы передаются сырыми `.gz` и распаковываются JS. Не добавлять им Content-Encoding:gzip поверх текущего формата и не распаковывать дважды.
- Сохранять `?v=<filesVersion>`, кодировку URL, `%23` для символа `#`, регистр путей. Не подменять файлы одной версии файлами другой.
- Текущий `fetch(url)` не требует preflight. Неработающий OPTIONS сам по себе не означает неработающий текущий загрузчик. Не добавлять custom headers/credentials в тест без причины.
- Облачный preview на постороннем домене не становится localhost и может не входить в CORS allowlist. Запускать browser runner с локальным HTTP origin внутри среды и проверить `location.origin`.
- **Только если настоящий прямой GET не работает:** установить причину, сохранить запрос/ответ и браузерную ошибку; проверить Origin/URL/кеш. Если прямой CORS недоступен и это нельзя решить в среде, использовать временный локальный `/game/` reverse proxy из `827473c6` как явно отмеченный fallback. Не менять Nginx автоматически.

Чтобы кандидат получал данные напрямую, оставить движок/оболочку локальными, а в ТЕСТОВОЙ копии собранной оболочки задать `GAME_PATH = "https://fallout-nevada.ru/game/"` в `initFilesystem.mjs`. Отдельный запасной URL FRM в `mainmenu.mjs`, начинающийся `./game/FalloutNevadaEng/Patch001.dat/ART/INTRFACE/`, тоже должен указывать на этот сервер. Иначе часть данных всё ещё будет запрашиваться локально. Зафиксировать эти изменения тестовой конфигурации. Не загружать опубликованные JS/WASM вместо кандидата.

Штатной настройки base URL в нынешней оболочке нет; при последующей реализации её можно выделить отдельно. CMake копирует JS на configure, поэтому повторный configure может сбросить правки в каталоге сборки. Проверять фактически обслуживаемые файлы. Наличие CORS само по себе не меняет старый относительный GAME_PATH.

## 5. Обязательный baseline: весь действующий сайт

Выполнить следующие шаги для КАЖДОЙ строки матрицы, до перехода к кандидату:

1. Открыть прямой маршрут игры на сайте, проверить название/версию/язык. Дождаться настоящего игрового меню. Загрузка большого количества ресурсов может идти долго; отсутствие меню через 15 секунд не доказывает сбой. Отслеживать прогресс запросов и ограничивать ожидание разумным сроком с диагностикой.
2. Запустить новую игру штатным UI. Выбрать/создать персонажа. Дождаться управляемой карты, а не заставки или незавершённого диалога.
3. Сделать осмысленное действие: пройти несколько доступных тайлов, открыть инвентарь/диалог либо взаимодействовать с предметом. Зафиксировать узнаваемое состояние A: персонаж, карта/позиция, предметы, журнал или другой наблюдаемый признак.
4. Обычным сохранением записать A в свободный слот с коротким уникальным описанием, например `AUDIT-NV34-N-A`. Дождаться завершения записи; проверить данные IndexedDB, когда они доступны. Не ограничиваться наличием файла только в виртуальной FS.
5. Изменить состояние до B: например, пройти дальше или изменить инвентарь. Перезагрузить страницу сайта, сохранив тот же профиль/origin. Через меню загрузки загрузить сейв A и убедиться, что восстановилось A. После загрузки пройти/взаимодействовать ещё раз: кадр должен быть живым.
6. Проверить quicksave: первый F6 может показать выбор слота. Выбрать другой свободный слот, сохранить; изменить наблюдаемое состояние, нажать F6 ещё раз. Второй вызов должен действительно пройти быстрым путём без окна, если таков штатный режим этой версии. Записать, какой путь реально сработал; если окно осталось, это ещё не проверка пути без окна.
7. Снова изменить состояние, перезагрузить сайт и загрузить последний quicksave через штатное меню. Сверить последнее сохранённое состояние и проверить управление после загрузки.
8. Вернуться в веб-оболочку после завершённой записи. Отдельного «архива quicksave» нет: quicksave пишет в обычный слот (SLOTxx), как и обычное сохранение. Через `Скачать сохранение` / `Download save` скачать ПОЛНЫЕ архивы двух слотов: слота обычного сохранения (шаг 4) и слота quicksave (шаги 6–7). Сохранить оба архива: normal и quick. Скачать все файлы слота вместе, включая вложенные каталоги; не ограничиваться SAVE.DAT.
9. Проверить, что архив читается и содержит SAVE.DAT и остальные фактически созданные файлы: карты, AUTOMAP.SAV, sfallgv.sav, proto и т.п. Наличие ce.sav в старой версии не предполагать. Сформировать manifest/hash и пометить строку baseline PASS только после всех проверок.

При любом провале обязательного save/reload/load сайта остановить весь переход к обновлению. Сохранить проблемный архив, скриншоты до/после, логи, URL, версии, сеть и описание шагов. Не исправлять baseline-файлы, не ослаблять проверки и не пропускать игру.

## 6. Сборка кандидата

Версия Emscripten — та, что в `.github/workflows/ci-build-web.yml` (сейчас 4.0.8); в docker-командах `emscripten/emsdk:<эта версия>`:

Проверку второго origin выполнять в чистом профиле и контролировать версию файлов. Профиль baseline сохранять для повторных проверок сайта, а профиль кандидата изолировать от него.

## 7A. Обязательная совместимость: старые сейвы → кандидат

Только когда baseline всех строк PASS, для каждого folder:

1. Проверить совпадение набора данных/индекса с baseline. В новой оболочке выбрать ТОТ ЖЕ folder. Убедиться, что JS/WASM обслуживаются локально, а игра берётся из зафиксированного набора.
2. Через штатный импорт загрузить неизменённые baseline-архивы normal и quick в свободные слоты. Хеш исходных архивов должен совпадать с manifest. Проверить, что все файлы и вложенные каталоги попали в IDBFS. Не подправлять SAVE.DAT, не удалять «мешающие» файлы, не пересохранять старый сейв новым движком до первой проверки.
3. Запустить кандидата и загрузить каждый импортированный сейв штатным меню. Восстановить узнаваемые состояния из manifest; сверить персонажа, карту/позицию, инвентарь и остальные признаки. Пройти/взаимодействовать после загрузки. Прочитать логи, проверить отсутствие ошибок формата/недочитанных данных.
4. Проверить старый сейв без ce.sav: должен штатно отработать legacy fallback для перков. Исходный архив сохранять неизменным. Если у baseline ce.sav уже есть, проверять его фактический формат, а отсутствие тестировать отдельно на копии.
5. Из загруженного состояния сделать НОВОЕ сохранение кандидатом в другой слот. Проверить SAVE.DAT, ce.sav, sfallgv.sav, карты/автокарту/прототипы. Перезагрузить страницу, загрузить новый сейв, сверить состояние и работоспособность.

## 8. Регрессии затронутого кода

### Сохранение, единая финализация и отказы хранилища

- Обычное сохранение; первый F6 с выбором слота; последующий F6 без окна; циклические auto quicksave; quickload F7; загрузка через меню. Проверять реально пройденные ветки.
- После успешной операции все потоки закрыты, SAVE.DAT/sfallgv.sav/ce.sav/proto/maps и slotdat.ini записаны ДО последней ожидаемой синхронизации. После возврата управления немедленно перезагрузить страницу и проверить IDBFS/сейв/выбранный слот.
- Проверить CurrentSlot после смены слота, загрузки и отмены окна, если сохраняется поведение upstream. Быстрый путь не должен зависеть от lsgWindowFree. Не делать два параллельных sync одной базы; единый обработчик завершения должен покрывать все пути и не отмечать неполный сейв успешным.
- Ошибку sync/populate внедрять только в тестовой среде. Проверить передачу err, отклонение Promise, отсутствие ложного `IDBFS saved`, понятное завершение/сообщение. Отдельно проверить успешную запись, отсутствие API persist(), отказ persist() и отсутствие IndexedDB. Отказ persist() не равен отказу записи.
- Проверить неуспешный обработчик записи/восстановление BAK и отсутствие опубликованного частичного сейва. Не повреждать исходные baseline-архивы; отрицательные проверки выполнять на копиях.

### Конфиги и их миграция

- Активный cfg определяется через [Misc] ConfigFile: проверить fallout2.cfg, Nevada.cfg и config.cfg в наборах, которые их реально используют.
- Код уже пишет `[qol] walk_when_sneaking=1` в активный cfg и не держит отдельный блок в game_mouse.cc. Проверить Sneak без перка/с перком, Shift, настройку постоянного бега, повторный клик и бой. Опция должна действовать через штатную логику организации. NOT RUN.
- Код больше не считает `screen.resolution_x` признаком законченной миграции. Старый cfg без новых ключей должен получить legacy UI-значения; обязательные screen overrides оболочки остаются. Новый cfg с явно заданными UI-ключами должен их сохранить. NOT RUN.
- Подтверждённый пример Nevada English: ALTERNATE_AMMO_METRE=1 → ui.alternate_ammo_meter должен стать 1, раньше получался 0. Проверить также MAIN_MENU_SIZE и остальные переносимые параметры. Старые числовые значения нельзя слепо копировать: upstream нормализует/ограничивает допустимые значения (например, death_screen_size и end_slide_size ограничены 0–1).
- Проверить создание config/game#patch.cfg из ddraw/F2Res, стартовую дату/меню/настройки мода, приоритет модов и каталогов патчей. Проверить исходники, а не только наличие файла.
- Изменить настройки меню, перезапустить без save: активный cfg должен создаться заново. После загрузки сейва классические preferences могут восстановиться из SAVE.DAT — это ожидаемо. Screen/HiRes и новые UI-настройки не считать сохранёнными в классическом 80-байтном блоке.
- Постоянно хранится только data/SAVEGAME. Не монтировать весь data/конфиги в IDBFS. Проверить, что временный data/config-маркер исчезает, а сейв остаётся.
- ASYNCFETCHFS: создание/отсутствующий файл с правильным ENOENT, короткая перезапись без хвоста, truncate, rename/unlink, временная запись cfg и сохранность комментариев/неизвестных ключей. Старый подход с неверными errno не возвращать.

### Управление и графика

- Проверить мышь, левый/правый клик, отпускание кнопок, Escape, pointer lock до/после выхода, fullscreen браузера, изменение viewport, DPR 1 и 2, HiRes вкл/выкл, screen.scale 1/2. Сверить точку касания с положением курсора и выбранной целью.
- На touch: короткий tap, небольшое дрожание до порога 15, drag, long press, два пальца (правый клик/scroll), новые жесты организации на 3/4 пальца, инвентарь/диалог/карта мира. Touch-эмуляция не заменяет реальный Android/iOS; невозможность аппаратной проверки отмечать как ограничение.
- Принудительный touchscreen=true и PAN_MINIMUM_MOVEMENT=15 сейчас сохранить: прямой конфиг-замены с доказанной полной эквивалентностью нет. windowed=1/mouse_lock=0 обеспечивает абсолютный режим, но не тождественен всей прежней touch-логике. Не удалять хак только из-за похожего названия опции. Отдельно учесть JS requestPointerLock().
- Для замены C++ запрета HiDPI и mouse↔touch hints на ENV проверить исходную/новую реализацию при одинаковых параметрах. ENV задавать до SDL_Init/создания окна и до кеширования окружения. Проверить фактическую версию SDL. Если эквивалентность не подтверждается, сохранить C++-правку.
- Проверить ввод имени персонажа и описания сейва: английский, русский, пробелы, Backspace/Enter/Escape, начало/конец ввода, экранную клавиатуру. Это отдельный JS bridge startTextInput/stopTextInput, он не заменён INI.

### Объекты, карты, звук и сборки

- Обход объектов: несколько объектов на одном тайле, соседние тайлы, разные elevations, пустые списки и конец карты; соседний тайл не пропускается. Обе функции обхода elevation должны соответствовать организации.
- Сценарии уничтожения объектов/скриптов, очереди событий, смены карты и load/reset: сравнить с baseline. Очередь отложенного free=10 не считать доказанно заменённой новыми memory safety fixes. При необходимости отдельно native ASan, не заменяя им браузерный тест.

## 9. Как управлять игрой через Playwright

У веб-оболочки есть DOM. Например, выбор версии — `#select_game_<folder>`, запуск — `#start_<folder>`, HiRes — `#enable_hires_<folder>`, слот — `#showmenu_<folder>_SLOT01`. Эти селекторы работают до запуска и в оболочке импорта/экспорта.

**Внутри игры кнопки нарисованы в canvas. DOM-селекторов для «Новая игра» или предмета на земле нет.** Playwright не распознаёт их автоматически. Агент смотрит скриншот и выбирает действие; Playwright отправляет клавиши, движения/клики/касания. Для автоматического распознавания понадобился бы отдельный алгоритм/шаблон, это пока не реализовано.

В предыдущем тесте Nevada English использовались реальные горячие клавиши: `n` в меню → `t` для готового персонажа → F6 → Enter → текст описания → Enter. Это доказано только для проверенного сценария, не универсально для всех модов/экранов. Обычный save в текущем исходнике F4/Ctrl+S, load F5/Ctrl+L, quicksave F6, quickload F7; сверять с фактическим экраном и версией сайта.

```js
await page.locator('#start_FalloutNevadaEng').click();
// Дождаться меню и убедиться по скриншоту, что n сейчас означает New game.
await page.keyboard.press('n');
// Проверить, что открылся выбор персонажа, затем t/нужная кнопка.
await page.keyboard.press('t');
```

Клик по наблюдаемой точке canvas: u/v — координаты, выбранные по ТЕКУЩЕМУ скриншоту canvas, от 0 до 1.

```js
const canvas = page.locator('#canvas');
await canvas.screenshot({ path: 'before-move.png' });
const box = await canvas.boundingBox();
if (!box) throw new Error('Canvas is not visible');
// Сначала определить u/v по видимой доступной точке, а не угадать их.
await page.mouse.click(box.x + box.width * u, box.y + box.height * v);
await canvas.screenshot({ path: 'after-move.png' });
```

Mouse API принимает CSS-пиксели viewport. Не умножать boundingBox на DPR повторно. Если координаты взяты из логической игры 640×480, учитывать фактическое разрешение, scale, центрирование окна, поля/letterbox и размер canvas. Один набор координат не годится автоматически всем модам и HiRes.

Перед координатными действиями проверить pointer lock; при активном lock абсолютный клик может не передвинуть игровой курсор ожидаемым образом. Предпочитать горячие клавиши для меню и отдельно проверять мышь как пользовательский механизм. Не добавлять лишний click ради фокуса, если он может переместить персонажа или нажать кнопку. После каждого действия проверять фактический экран/состояние.

HTML select/download/import можно автоматизировать нормально. Для архива зарегистрировать `page.waitForEvent('download')` ДО клика и вызвать `download.saveAs(...)` ДО закрытия context: временный файл иначе может исчезнуть. В оболочке меню — `#contextMenu .context-menu-item`, выбирать точный текст «Скачать сохранение»/«Download save» и соответствующего импорта по текущей локализации. Input импорта создаётся динамически и может не быть добавлен в DOM: ждать `filechooser` до клика и передать `fileChooser.setFiles(path)`. Не предполагать наличие постоянного input selector.

Доказательства состояния собирать несколькими способами: скриншот, действия после загрузки, файлы/IndexedDB и диагностические логи. Проверка JS FS допустима как дополнительная проверка. Прямая запись памяти/телепортация/вызов saveGame через evaluate не заменяет пользовательский сценарий.

Не читать незагруженный ASYNCFETCHFS-файл через FS.readFile из page.evaluate: можно вызвать Asyncify rewind вне стека Wasm. Читать node.contents уже загруженного файла либо отдельно fetch исходника; IDBFS-файлы доступны в памяти. Не считать произвольный таймаут или networkidle доказательством окончания игрового действия. У игры нет DOM auto-wait для состояния canvas.

Справка Playwright: [клавиши и действия](https://playwright.dev/docs/input), [координаты мыши](https://playwright.dev/docs/api/class-mouse), [скачивание](https://playwright.dev/docs/downloads), [file chooser](https://playwright.dev/docs/api/class-filechooser).
